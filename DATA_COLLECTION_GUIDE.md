# Data Collection Guide

My personal reference for operating this project during the collection phase.
Everything here comes from the current code in this repo.

**Two things that matter most:**

1. A normal run records **real `PILOT` data** by default. No special flag needed —
   `--storage-config` already defaults to `config/storage.pilot.yaml`.
2. **Days matter more than hours.** The evaluation splits by calendar day, so 1 hour
   on 5 separate days beats 10 hours on one day.

Collection only works on **Windows, natively**. Docker Compose cannot collect — it
has no way to install Windows input hooks or reach the named pipe.

---

## A. First-time setup (do this once)

### A1. Requirements

- Windows 10 or 11
- Python 3.11+
- Node.js 22 + npm
- CMake 3.20+
- Visual Studio Build Tools with the "Desktop development with C++" workload
- Permission to install global keyboard/mouse hooks (some antivirus blocks this)

Run everything from the repo root: `C:\Users\Manas\Desktop\manas_ml-pipeline`

### A2. Python environment

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -e ".[backend,dev]"
```

### A3. Build the dashboard

```powershell
Set-Location dashboard
npm ci
npm run build
Set-Location ..
```

This produces `dashboard/dist`, which the backend serves itself. **There is no
separate dashboard server.**

### A4. Build the collector

```powershell
cmake -S collector -B build/collector -DBUILD_TESTING=ON
cmake --build build/collector --config Release
ctest --test-dir build/collector -C Release --output-on-failure
```

The exe lands at `build\collector\Release\continuous_auth_collector.exe`.
If `ctest` passes, this machine can run the collector.

### A5. Verify everything is ready

```powershell
python protocol/codegen/generate.py --check
python tools/guardrails/check.py
python -m pytest
```

All three must pass before collecting anything.

Then confirm the **pilot** storage profile itself is valid (validates only, creates
nothing):

```powershell
python -m backend.app.storage.cli check --config config/storage.pilot.yaml
```

Expect `T-009 storage configuration is valid (no data was created).`

> The `--config` flag matters. Its default is `storage.development.yaml`, so running
> this bare checks the *wrong* profile.

### A6. Pick a pseudonym — once, permanently

Must match `^[A-Za-z0-9_-]{8,64}$` — letters, digits, hyphen, underscore only, 8–64
characters. No name, email, or roll number. Example: `manas-01` (exactly 8, so don't
shorten it further).

**Never change it.** All data is grouped under this string. Changing it mid-round
splits one person into two and ruins the corpus.

### A7. Do I need to "enroll" before collecting?

**No.** Collection only needs the pseudonym passed to the backend.

The word "enrollment" shows up twice in this repo and neither one blocks collection:

| Thing | What it is | When |
|---|---|---|
| `data/collection/administration.json` | A **hand-written** JSON file with `consents` and `enrollments` arrays | Only needed to run `health` / `freeze`. Not generated by any tool. |
| `python -m tools.enrollment activate` | Trains the **first ML model** from a frozen corpus | **After** collection finishes, not before |

**Create `data/collection/administration.json` by hand before day 1.** It isn't
needed for the collector to run, but the health check, the freeze, and the first-model
enrollment gate all read it, and a consent/enrollment timestamp *after* your first
collection day marks those earlier windows ineligible (`BEFORE_ENROLLMENT`). Easier to
write it up front than to argue with it later.

Shape required by `tools/collection/repository.py`:

```json
{
  "consents": [
    {
      "participant_id": "manas-01",
      "protocol_revision": "v1",
      "consented_at": "2026-09-05T09:00:00Z"
    }
  ],
  "enrollments": [
    {
      "participant_id": "manas-01",
      "enrolled_at": "2026-09-05T09:00:00Z",
      "collector_version": "t005-windows-development-v1",
      "protocol_version": "1.0.0"
    }
  ]
}
```

Timestamps must include a timezone. `data/` is git-ignored.

## B. Starting the system

### Step 0 — once per PowerShell session, before Terminal 1

```powershell
$artifactRoot = Join-Path $env:LOCALAPPDATA "ContinuousAuthentication\Pilot\models"
New-Item -ItemType Directory -Force $artifactRoot | Out-Null
$env:CA_DASHBOARD_SECRET = Read-Host "Dashboard password"
```

The backend refuses to start without `CA_DASHBOARD_SECRET`. Use the same password
every day — you type it into the dashboard login.

### Terminal 1 — backend + ML + API + dashboard  ← START THIS FIRST

```powershell
.\.venv\Scripts\Activate.ps1
python -m backend.app.runtime.cli `
  --participant-id manas-01 `
  --artifact-root $artifactRoot `
  --dashboard-directory dashboard/dist
```

Opens the SQLite/WAL database, starts a `PILOT` collection session, creates the
Windows named pipe `continuous-auth-v1`, and serves the API + WebSocket + built
dashboard at `http://127.0.0.1:8765`.

> `$artifactRoot` and `$env:CA_DASHBOARD_SECRET` must be set in *this* terminal.

### Terminal 2 — native event collector

```powershell
.\build\collector\Release\continuous_auth_collector.exe `
  --config config/collector.development.yaml `
  --categories config/app_categories.yaml
```

Installs the global keyboard/mouse hooks and streams framed, content-free events
over the named pipe.

### Order rule

Backend **first** — it creates the pipe. If you start the collector first it just
retries with backoff until the pipe appears, so getting it wrong is not fatal.

Both processes must run as the **same Windows user**.

> **Alternative (packaged install only):** `deployment\windows\run-development.ps1
> -ParticipantId manas-01` starts both in one command — but only against an
> installed package under `%LOCALAPPDATA%\ContinuousAuthentication\Application`,
> not this repo checkout. For working from the repo, use the two terminals above.

## C. Dashboard

### How it starts

It doesn't — it's already running. The backend serves `dashboard/dist` on
**<http://127.0.0.1:8765>** as soon as Terminal 1 is up.

### What to do in it

1. Open <http://127.0.0.1:8765>
2. Sign in with `CA_DASHBOARD_SECRET`
3. **First time only:** a *Security Challenge Setup* screen appears — pick a
   question and answer. Stored only locally, only as a hash. Change it later in
   **Settings** (needs the current answer).

After that, signing in each morning is just a liveness check.

### How I know collection is working

Open the **System health** view. Look for:

- **Health** — a status, not `UNAVAILABLE`
- **Dropped events** — should stay at **0**
- **Collector CPU / memory** — should show real numbers, not `N/A`
  (`N/A` means the collector isn't reporting → check Terminal 2)
- **Components** — the component list populated

Then type and move the mouse for a few minutes and check that activity appears.

**How long before data appears:** a feature window closes after **30 seconds** or
**100 keystrokes**, whichever comes first (`config/ml.development.yaml`). So expect
the first window within about a minute of real typing — not instantly, but not long.

### Two command-line checks (faster than the UI)

Liveness, no login needed:

```powershell
Invoke-RestMethod http://127.0.0.1:8765/healthz
```

**Am I actually recording real data?** This one is worth running on day 1 — it reads
the storage settings directly, so it cannot disagree with what's on disk:

```powershell
$s = Invoke-RestMethod http://127.0.0.1:8765/v1/auth/login -Method Post `
  -ContentType application/json `
  -Body (@{ local_secret = $env:CA_DASHBOARD_SECRET } | ConvertTo-Json) `
  -SessionVariable ca
Invoke-RestMethod http://127.0.0.1:8765/v1/collection/provenance -WebSession $ca
```

Expect `environment: PILOT`, `data_policy: APPROVED_COLLECTION`,
`collection_provenance: PILOT`. If it says `DEVELOPMENT` / `SYNTHETIC`, you started
with the wrong `--storage-config` and **the data will not count** — stop and restart.

### What is NOT a problem

- Risk state `INSUFFICIENT_DATA` while idle — correct behaviour, not a fault.
- "Protection unavailable" / no risk score early in the round — there is no trained
  model yet. The system is being honest. Do not try to fix this.
- **`model: UNAVAILABLE` in the components list** — same reason. It reads `HEALTHY`
  only once a profile is active, which can't happen until after the round is frozen
  and `tools.enrollment activate` has run. `collector` and `storage` are the two you
  actually care about during collection.
- **Health `DEGRADED`** — expected *if you paused*. See §E.

## D. Daily data collection

### D1. Morning

1. Start PC, open PowerShell in the repo root.
2. Run the **Step 0** block (artifact root + password).
3. **Terminal 1** — start the backend.
4. **Terminal 2** — start the collector.
5. Open <http://127.0.0.1:8765>, sign in, check **System health**.
6. Minimise both terminals. **Leave them running.**

### D2. During the day

Use the computer completely normally. Don't perform, don't type carefully, don't
avoid anything. Browsing, coding, writing, messaging — all of it is useful data.

Optionally glance at System health once mid-day: dropped events still 0.

### D3. End of day

1. `Ctrl+C` in **Terminal 2** (collector) — removes the global hooks.
2. `Ctrl+C` in **Terminal 1** (backend) — closes the pipe, database, and audit
   files cleanly.
3. Verify the data (optional but recommended):

```powershell
python -m tools.collection --config config/collection.pilot.yaml health `
  --database "$env:LOCALAPPDATA\ContinuousAuthentication\Pilot\continuous-auth.db" `
  --administration data/collection/administration.json
```

Look at `distinct_days` and `total_windows` going up day over day.

4. Shut down the PC normally.

### D4. Next day

Exactly the same as D1. Nothing to restore, nothing to re-enroll. The database
already exists and new windows are appended under the same pseudonym and a new
collection day.

## E. Stop / pause / resume

### Safe stop

`Ctrl+C` — collector first, then backend. Do not close the window with the X while
the backend is mid-write if you can avoid it (though see §F on durability).

If the terminal stays open afterwards and you want to clear the secret:

```powershell
Remove-Item Env:CA_DASHBOARD_SECRET
```

### Pause / resume — yes, this really exists

Implemented via a named Windows event (`tools/collection/pause.py`), with the name
`continuous-auth-pause-v1` from `config/collector.development.yaml`.

Pause (in a third PowerShell, venv active, while both processes are running):

```powershell
python -m tools.collection --config config/collection.pilot.yaml pause `
  --event-name continuous-auth-pause-v1
```

Resume:

```powershell
python -m tools.collection --config config/collection.pilot.yaml resume `
  --event-name continuous-auth-pause-v1
```

**How to confirm the pause actually took:** the collector keeps sending heartbeats
while paused, but they carry `collection_paused`, and the backend turns that into
**Health = `DEGRADED`** with component `collector: DEGRADED`
([orchestrator.py:445-447](backend/app/runtime/orchestrator.py#L445-L447)). So on the
dashboard: `DEGRADED` = paused and working correctly, not broken. Still `HEALTHY`
after you ran `pause` means the pause did **not** take — check the event name.

Notes:
- `--config` is required by the argument parser even for pause/resume.
- Windows-only. It raises `PauseControlError` anywhere else.
- Use this for short breaks (private typing, someone else using the machine). For
  overnight, just stop both processes.

### Resuming the next day

There is **no separate "resume session" command** and none is needed. Each backend
start opens a new session; the corpus accumulates per participant per collection
day. Restarting is the normal mechanism — just run §D1 again with the **same
pseudonym**.

## F. Data persistence

### Where it lives

| What | Path |
|---|---|
| Data root | `%LOCALAPPDATA%\ContinuousAuthentication\Pilot` |
| Database | `%LOCALAPPDATA%\ContinuousAuthentication\Pilot\continuous-auth.db` |
| Audit records | `%LOCALAPPDATA%\ContinuousAuthentication\Pilot\audit` |
| Model artifacts | `%LOCALAPPDATA%\ContinuousAuthentication\Pilot\models` |

Nothing is written inside the repo, and `data/` is git-ignored. Never commit any
of it.

### Does data survive shutdown?

**Yes.** The store is SQLite with `journal_mode = WAL` and `synchronous = FULL`, so
every committed feature window is on disk before the write returns. Audit records are
`fsync`'d per record. There is no batching layer.

One detail worth knowing: **`Ctrl+C` saves slightly more than a force-kill.** A clean
shutdown ends the session and flushes the *partially built* window (up to 30 s / 100
keystrokes of input). `taskkill /F` or a power cut loses that one window. Everything
before it is already safe either way — so this is a reason to prefer `Ctrl+C`, not a
reason to panic if the machine dies.

### Do I need to do anything before shutting down?

**No.** `Ctrl+C` both processes and shut down. That's it.

The only real rule: **do not copy or zip the database while the backend is running**
— stop it first, or you can get a torn copy.

### Do I need to re-enroll or reconfigure the next day?

**No.** Just the same start commands with the same `--participant-id`.

### Retention

`config/storage.pilot.yaml` keeps feature windows and scores for **120 days**, so a
normal collection round is in no danger of ageing out.

## G. Troubleshooting

**`collector hook startup failed`**
Antivirus or policy is blocking global input hooks. Cannot be worked around and
should not be. This machine can't be used for collection.

**Dashboard won't open / login fails**
- Is Terminal 1 still running?
- Are you using the password set *before* the backend started? Setting
  `CA_DASHBOARD_SECRET` after startup does nothing.
- Is something else on port `8765`?
- Is `dashboard/dist` built and `--dashboard-directory dashboard/dist` present?

**Collector keeps reconnecting**
- Start the backend first.
- Both must run as the same Windows user.
- Both must be pointed at `config/collector.development.yaml` (pipe name
  `continuous-auth-v1`).

**`production named-pipe ingestion requires Windows`**
You started the full runtime on Linux/macOS/WSL/Docker. Run it natively on Windows.

**No data appearing / health says protection unavailable**
- Confirm collector CPU/memory are not `N/A` on System health.
- Confirm the collector terminal has no errors.
- "Protection unavailable" with no trained model is **expected** early on. Only
  worry if *dropped events* climb or the collector shows `N/A`.

**Backend won't start: "storage root_directory cannot be inside a cloud-synchronised
folder"**
Your `LOCALAPPDATA` resolves into OneDrive / Dropbox / Google Drive / iCloud. The
storage layer refuses these on purpose (a syncing SQLite file corrupts). Same for
`must be outside the source workspace`. Fix the folder redirection — don't work around
it by editing the config.

**Backend or collector crashes mid-day**
Data already committed is safe. Restart: backend first, then collector, same
pseudonym. Then check System health.

## Quick reference

| | |
|---|---|
| Dashboard | <http://127.0.0.1:8765> |
| Data folder | `%LOCALAPPDATA%\ContinuousAuthentication\Pilot` |
| Database | `...\Pilot\continuous-auth.db` |
| Pseudonym | `manas-01` (never change) |
| Stop | `Ctrl+C` — collector, then backend |
| Pause event name | `continuous-auth-pause-v1` |
| Minimum collection days | **3** (`freeze.min_distinct_days` — needed to split at all) |
| Minimum for a first model | **4** (gives a 2-day TRAIN partition) |
| Target for this round | 4 days — **already met**; see below |
| Minimum per day | 50 windows (`collection.min_windows_per_day`) ≈ 25 min active input |

> **Three different day thresholds exist and they answer three different questions.**
> They used to be conflated, which is what produced the earlier "plan for 5" advice.
>
> | Setting | Question it answers | Scope | Value |
> | --- | --- | --- | --- |
> | `config/collection.pilot.yaml → freeze.min_distinct_days` | "Can this corpus be split day-disjointly at all?" | whole collection | 3 |
> | `config/ml.development.yaml → enrollment.min_train_distinct_days` | "How many distinct days must a **first model** be trained on?" | frozen TRAIN partition only | 2 |
> | `config/risk.development.yaml → enrollment.min_distinct_days` | "How much has the runtime observed before this user stops being `ENROLLING`?" | the user's whole live history | 3 |
>
> The freeze reserves one whole day per TRAIN/VALIDATION/EVALUATION partition and then
> distributes 60/20/20, so collection days map to TRAIN days like this:
>
> | Collection days | TRAIN | VALIDATION | EVALUATION | First model possible? |
> | --- | --- | --- | --- | --- |
> | 3 | 1 | 1 | 1 | no — one day cannot define a baseline |
> | **4** | **2** | **1** | **1** | **yes** |
> | 5 | 2 | 2 | 1 | yes, and TRAIN is unchanged |
> | 6 | 3 | 2 | 1 | yes |
>
> **This round has 4 days (2026-09-05 … 09-08) and that is enough.** A 5th day would
> produce an identical 2-day TRAIN partition and change nothing. Do not collect extra
> days to satisfy a threshold — see ADR-014.

## Not part of daily collection

These run **once, after** the collection round — don't confuse them with daily steps:

- **Freeze the corpus** (write-once, day-disjoint, checksummed):

```powershell
python -m tools.collection --config config/collection.pilot.yaml freeze `
  --database "$env:LOCALAPPDATA\ContinuousAuthentication\Pilot\continuous-auth.db" `
  --administration data/collection/administration.json `
  --version pilot-v1 --output data/frozen/pilot-v1/manifest.json
```

- **Train + activate the first model** from that frozen corpus:

```powershell
python -m tools.enrollment activate `
  --participant-id manas-01 `
  --database "$env:LOCALAPPDATA\ContinuousAuthentication\Pilot\continuous-auth.db" `
  --manifest data/frozen/pilot-v1/manifest.json `
  --administration data/collection/administration.json `
  --artifact-root $artifactRoot `
  --ml-config config/ml.development.yaml `
  --risk-config config/risk.development.yaml
```

`--ml-config` and `--risk-config` have **no defaults** — there is no
`config/ml.pilot.yaml` or `config/risk.pilot.yaml` in this repo, so they must be
named explicitly.

Expected output, for a single-participant corpus:

```json
{"validation_code": "ENROLLMENT_INITIAL_PROFILE_NO_IMPOSTOR_COHORT",
 "validation_far": null,
 "validation_frr": <a real number>}
```

`"validation_far": null` means **not measured** and is the correct result — a
false-acceptance rate needs impostor data, and there is no second participant. If you
ever see `0.0` there, stop: that number would be fabricated. FRR *is* measured, on the
held-out VALIDATION day, at the operating point the live system actually uses.

- **Run the attacker drill** — but only **after** freezing and activating. Full
  procedure: `docs/pilot/attack-drill-protocol.md`.

```powershell
python -m backend.app.runtime.cli `
  --participant-id manas-01 --artifact-root $artifactRoot `
  --drill-label drill-01
```

`--drill-label` marks the whole session as an attacker drill. Its windows are scored,
risk-assessed, and enforced exactly like real ones — that is the point — but they are
permanently excluded from every training, calibration, validation, enrollment, and
update corpus. **Never use it for genuine collection**, and never freeze a corpus after
a drill without checking the manifest excludes it.

**Ordering matters and is not negotiable:** stop collection → freeze → activate →
shadow period → enable enforcement → drill. Freezing first is what makes "the attacker
never touched the training data" checkable from timestamps alone.

Also: `updates.development.yaml` sets `quarantine_days: 7`, so don't schedule the
first `tools.updates run` before roughly **day 12** of the round. For this
single-participant pilot that run refuses immediately with
`UPDATE_REQUIRES_IMPOSTOR_COHORT` regardless of the day — model updates are
intentionally disabled here, because a candidate's FAR cannot be measured without an
impostor cohort. Nothing is broken; see `docs/update-manager.md`.
